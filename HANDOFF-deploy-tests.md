## Useful things learned this session (apply to your work too)

- **`create-service-instance` needs `name` nested inside `config`**, not as a sibling top-level argument, e.g. `{"serviceId": "...", "config": {"name": "foo", ...}}`. A top-level `name` gives a confusing "Missing required fields: name" error even though it was supplied.
- **`update-my-app-source-ref` to the SAME branch name does not reliably pick up new commits** on that branch, even though it claims to trigger a rebuild — I observed it serve a stale commit after pushing new commits to a branch it was already pinned to. Use `restart-my-app({ rebuild: true })` instead when you need to force a fresh clone of the latest commit on the current branch.
- **To trigger a rebuild after pushing new code to a branch an app is already deployed from**: `restart-my-app({ appId, rebuild: true })`, then `wait-for-app-ready({ appId, awaitNewGeneration: true })`.
- **To read build/runtime logs**: `get-my-app-logs({ appId, tail: N })` (no filter — the `level: "error"` filter often returns nothing useful since most runner output is plain stdout, not literally containing "error"). For a fuller picture including build phase and detected issues, `diagnose-my-app({ appName })` is more thorough than `get-my-app` and worth calling first when something looks wrong.
- **`get-my-app` uses `appId` as the parameter name; `diagnose-my-app` uses `appName`** — passing the wrong key name gives a Zod validation error, not a helpful hint.
- **Always re-check `get-active-workspace` returns `simonwork` immediately before every write call** (create/delete/restart) — Simon asked for this explicitly and it costs almost nothing.
- **Deleting a My App that failed to build cleanly (e.g. `setup.sh` exit 1, bad branch, private-repo-without-token) works fine and leaves no orphan.** The orphan bug I hit (`phpdeploy`, see the Composer case above) happened specifically after a **Composer install failure** — that may be the specific trigger, worth testing again to see if it reproduces on a fresh app name if you want to confirm the root cause before it goes in a ticket candidate list.
- **`wait-for-app-ready` can be fooled by a 200 status from a broken app** (see the no-index case) — don't trust `readyStatus: "READY"` alone; if something seems off, always cross-check with `diagnose-my-app` and a manual `curl` of the real stable URL before declaring success.
- Local PHP for testing: Homebrew's `php` (currently PHP 8.5.x) is installed on this Mac and `php -l` is fast for syntax-checking before pushing. Composer is at `/tmp/composer` (`php /tmp/composer ...`). **When generating any `composer.lock` intended to run on the actual php-runner, force `"config":{"platform":{"php":"8.3.35"}}`** in `composer.json` before running `composer update`, otherwise local PHP 8.5 will happily lock packages that require PHP >=8.4 and the deploy will fail for a boring, unrelated version-mismatch reason (this bit me on the vulnerable-lock case).
- Postgres for local testing: already installed and running locally (`pg_isready` succeeds), `createdb`/`psql` available under the `simon` user.
- Composer's newer built-in advisory-blocking resolver refuses to lock a package with known security advisories by default; to intentionally generate a lock pinning a vulnerable version (needed for the vulnerable-lock case), add `"config":{"policy":{"advisories":{"block": false}}}` to `composer.json` before `composer update`, then you can strip that key back out of `composer.json` before committing (the lock file itself is what matters for this test, not the config that generated it).

Do not rename or force-push over these — future readers of this handoff may want to re-check them.
